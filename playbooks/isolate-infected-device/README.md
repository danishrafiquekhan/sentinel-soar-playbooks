# isolate-infected-device

Not built yet. Design notes so far:

## What it's supposed to do
When Defender for Endpoint raises a high-severity malware alert (active payload, not just a detected-and-quarantined signature match) and it lands in Sentinel through the Defender connector, isolate the affected device from the network before the analyst has even opened the incident. This is the one alert type in this repo where speed matters more than getting a human to confirm first — ransomware doesn't wait for triage, and a device that's already isolated when the analyst picks up the case is a device that didn't spend the last ten minutes encrypting a file share.

## Why this shape
Sentinel version: Logic App triggered off the automation rule, filtered down to a specific severity/alert-category combination (not every Defender alert, just the ones that mean "active malicious code executing," which is a narrower and more deliberate filter than it sounds — most Defender alerts are informational or already auto-remediated by Defender itself). On match, it calls the Defender for Endpoint API directly: `POST /api/machines/{id}/isolate` with `isolationType: Selective`, which cuts general network access but leaves the Defender management channel up so the box stays reachable for investigation instead of going fully dark. That needs `Machine.Isolate.All` on the app registration (application permission, not delegated — this has to run with no signed-in user behind it), plus `Machine.Read.All` to resolve the device ID from the alert in the first place. Selective over full isolation is the deliberate choice here: full isolation is for when you're sure, and an automation rule reacting to one alert category is not "sure" the way an analyst who's looked at the process tree is.
Local version (see `../../local-lab/`): there's no real equivalent — Cortex doesn't have a Defender for Endpoint responder in its analyzer catalog by default, and I'm not running an actual EDR agent in `local-lab/` to isolate in the first place. Best I could do locally is a Cortex responder that logs what it *would* have called and stops there, which felt more like theater than a useful lab artifact, so I didn't build it. This one only really exists as the Sentinel design.

## What's left manual
Un-isolating. On purpose — that's `POST /api/machines/{id}/unisolate`, same permission, and I don't want that call anywhere near an automation rule. Selective isolation buys time, it doesn't mean the device is clean, so bringing a machine back onto the network is a decision that needs a completed investigation behind it, not a webhook. Also manual: anything past the single device — this playbook doesn't look at whether other machines show the same indicators, it isolates the one box the alert actually named and stops. Lateral-movement hunting off the back of it is a human's job.
